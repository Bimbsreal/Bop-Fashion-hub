# Bop media asset architecture

Status of this document: written after `sql/migrations/003_media_files.sql` was applied to the disposable local PostgreSQL 18 cluster and the media tests passed. Earlier notes live in `docs/bop-core-domain-architecture.md` and `docs/bop-fashion-catalog-architecture.md`. The platform audit predates this schema.

Labels:

- **IMPLEMENTED** — present and exercised.
- **PARTIALLY IMPLEMENTED** — a real boundary exists, but only part of the behavior.
- **PLANNED** — reserved, not built.
- **NOT IMPLEMENTED** — intentionally absent.
- **NOT VERIFIED** — not checked in this phase.

Landing-page files were not moved or renamed. The African fashion film still uses the local file `footer video.mp4`.

## 1. Existing media architecture

**IMPLEMENTED** by extending `media_assets` and `garment_media`. No second media table was added.

Before this phase, the catalog could register metadata and a storage key, with status `pending`, and no file behind the key. That metadata path remains for callers that are not uploading bytes. The upload path is separate and writes a file only after the bytes pass image validation.

`garment_media.role` is still the garment purpose: `primary`, `front`, `back`, `side`, `detail`, `fabric`, `sketch`, `construction`, `reference`, or `generated`. Ownership is still one user or one organization.

## 2. Implemented media metadata model

**IMPLEMENTED** on `media_assets`.

| Field | Role |
| --- | --- |
| `id` | Media identifier |
| `owner_user_id` or `owner_organization_id` | Exactly one owner |
| `original_filename` | Display name only. Paths and `..` are removed. It is not the storage location. |
| `storage_key` | Opaque relative key. Unique. It is not returned by the media API. |
| `mime_type` | Taken from the decoded image, not from the client header |
| `byte_size` | Size of the stored bytes |
| `media_type` | `image` for uploads. `video` and `other` remain available to the older metadata call |
| `width_px`, `height_px` | Oriented dimensions |
| `status` | `pending`, `ready`, or `failed` |
| `visibility` | `private` or `public` |
| `variant` | `original` or `thumbnail` |
| `derivative_of_id` | Set only on a thumbnail. Deleting the original deletes the thumbnail row |
| `created_at`, `updated_at` | Timestamps |

There is still no `bytea` column. Duration is **NOT IMPLEMENTED**. A separate media-purpose column was not added, because garment purpose already lives on `garment_media`.

## 3. Storage abstraction

**IMPLEMENTED** as a small `MediaStorage` interface in `server/src/modules/storage.ts`: `write`, `read`, and `remove`. Domain code depends on that interface. `localMediaStorage` is the local implementation.

The root cannot be the `public` directory, so landing assets cannot become the upload store. Keys are generated by the server as `originals/{id}.ext` and `thumbnails/{id}.ext`. User filenames and request paths are not used. Writes use a create-only flag, so one key cannot overwrite another file.

Object storage is **PLANNED**. Replacing `localMediaStorage` should not require a new media table.

## 4. Local storage configuration

**IMPLEMENTED.**

- Default directory: `.local/media`
- Override: `MEDIA_STORAGE_DIR`
- Default maximum upload: 8388608 bytes (`MEDIA_MAX_BYTES`)
- Default maximum edge: 8000 pixels (`MEDIA_MAX_EDGE`)
- Decode cap: 40 megapixels

`.local/` is gitignored. The directory is not served as a static route. Tests used `.local/media-test` and removed it afterward.

## 5. Upload validation

**IMPLEMENTED** for JPEG, PNG, and WebP. The body is the file. `Content-Type` is not trusted.

- The decoded format must be JPEG, PNG, or WebP. GIF and non-images are rejected.
- A real JPEG sent as `text/plain` is accepted and stored as `image/jpeg` or the detected MIME type.
- Empty files, unreadable bytes, and images over the edge limit are rejected.
- The raw parser rejects bodies over the byte limit with HTTP 413.
- The original bytes are stored unchanged. A thumbnail, longest side 480, is a second file and a second row.
- Each user is limited to 30 uploads a minute in that API process. This limit is **PARTIALLY IMPLEMENTED**: it is not shared across processes.

Video upload and video processing are **NOT IMPLEMENTED**.

## 6. Media access control

**IMPLEMENTED** on the server.

- Private media metadata and bytes are available to the owning user, or to an active member of the owning organization.
- Anyone else, including someone who knows the id, receives 404.
- Public media bytes can be read without a session.
- Public visibility does not grant edit or delete.
- Organization media is not readable by a member of a different organization.
- `GET /api/v1/media/:id/content` is the only byte route. Responses set `X-Content-Type-Options: nosniff` and `Cache-Control: private, no-store`.
- The media JSON does not include `storageKey` or a disk path.

Collaborator grants and signed URLs are **NOT IMPLEMENTED**.

## 7. Processing lifecycle

**PARTIALLY IMPLEMENTED.** Validation is synchronous, so there is no queue.

- Metadata registered without a file stays `pending`.
- An upload row is inserted as `ready` only after decode, thumbnail creation, and the file write have succeeded.
- `failed` remains a legal status and is not written by this path.
- `uploaded`, `validating`, `processing`, and `deletion pending` were not added.

If the database transaction fails after a file write, the API deletes the files it just wrote. A test covers a failed follow-up insert by linking a missing garment: the response is 404 and the storage map is empty. Filesystem and PostgreSQL still cannot share one atomic commit. A crash between deleting a file and committing the database transaction can leave a mismatch. That window is **NOT VERIFIED** under a killed process.

## 8. Media-to-garment relationships

**IMPLEMENTED** with the existing `garment_media` table. An upload may include `garmentId` and `role`. The garment and the media must have the same owner. The link is rejected when the garment does not exist, and the new files are removed.

No polymorphic table was added for designers, AI jobs, try-on sessions, or commerce products. Those associations are **PLANNED** as their own foreign keys when those tables exist. A generic owner-type column would not enforce those relationships.

## 9. Retention and deletion

**PARTIALLY IMPLEMENTED.** `DELETE /api/v1/media/:id` is allowed for an editor.

The transaction removes garment links and the media row. An original delete also removes its thumbnail row. The stored files are removed in that same transaction; if removal throws, the database change rolls back. Missing files are ignored. The deletion test confirmed the metadata row was gone and a later content request returned 404.

There is no retention schedule and no audit table. Deleting the row does not claim to erase copies outside this storage root. Image bytes and passwords are not written to logs.

## 10. API endpoints

**IMPLEMENTED** at `http://127.0.0.1:5000/api/v1`.

- `POST /api/v1/media` — authenticated upload. Optional query: `visibility`, `organizationId`, `garmentId`, `role`. Optional header: `X-Original-Filename`.
- `GET /api/v1/media` — originals the caller can access. Anonymous callers see public originals only. `limit` and `offset` match the catalog page limits.
- `GET /api/v1/media/:id` — metadata.
- `GET /api/v1/media/:id/content` — bytes when allowed.
- `DELETE /api/v1/media/:id` — editor only.

`GET /api/v1/health` is unchanged. The catalog metadata attachment route remains for callers that are not sending a file.

## 12. Tests and results

**IMPLEMENTED** in `server/test/media.test.ts`, together with the existing foundation and catalog files, via `npm test`.

Covered:

- Public directory rejected as a storage root
- Unsafe filenames reduced to a base name
- Stored files removed when the following database step throws
- PNG accepted from its bytes when the client type is `text/plain`
- Non-image bytes rejected when labeled `image/png`
- GIF rejected
- Original bytes returned unchanged to the owner
- Thumbnail is a different, smaller image
- Anonymous and other users cannot read a private file
- Public read, then delete, then 404 and no metadata row
- Organization isolation and a `fabric` garment link
- A missing garment leaves no stored file
- Oversize bytes, oversize dimensions, and the per-minute upload limit

The verification run passed 20 tests, including the foundation and catalog suites. Lint, typecheck, and the production build were run after that and are reported in the phase summary.

## 13. Future object-storage integration

**PLANNED.** Implement another `MediaStorage` for the provider. Keep `storage_key` as the provider key. Do not put the provider client in garment or fashion modules. No paid provider is configured.

## 14. Future AI-processing integration

**NOT IMPLEMENTED.** No image is sent to an external service. No AI result is fabricated. A later job should reference `media_assets.id` for its input and should create a new media row for its output, with the same ownership check. Try-on, measurement extraction, fit, and styling are not part of this engine.

## 15. Known limitations

- Video uploads are **NOT IMPLEMENTED**.
- Only JPEG, PNG, and WebP are accepted.
- The thumbnail is the only derivative. A separate preview or display-optimized variant is **NOT IMPLEMENTED**.
- Upload rate limiting is local to one process.
- Collaborator sharing, signed URLs, retention schedules, and an audit log are **NOT IMPLEMENTED**.
- Metadata-only catalog registration can still store a key with status `pending` and no file. Its content route returns 404.
- The landing page does not upload media.
